# 12. 双模型架构：传统生成器 teacher（A）× RSI-Reap 求解器 student（B）

§11 的写法混淆了两者。真实设计是 **两个分工不同的模型**：

| | 模型 A: teacher | 模型 B: student |
|---|---|---|
| 训练方式 | **传统三段式**：pre-train → SFT → post-train，**推理时冻结** | **新式 RSI-Reap**：MCTS + 验证回馈 + 测试时更新（§09 TTT）+ 递归代际演化（§10） |
| 任务 | 生成问题：难题 $p_*$ 的**简化/相似变体**、提示、引理外置建议 | 求解题目：在重 MCTS 搜索、在线更新、代数演化中逼近 $p_*$ |
| 更新时机 | 只有训练阶段（批式、可回滚） | 推理中也更新（TTT）+ 代际重训 |
| 参考 | 任何通用 LLM API（或自己传统后训练的钱德） | reap 改造版 |

## 12.1 协作环路

```
                    A: teacher (传统, 推理冻结)
                     │  输入：难题 p_*  + 库上下文 ctx(L_g)
                     │  输出：变体阶梯 v_1 ≺ v_2 ≺ … ≺ p_*
                     ▼
        ┌────────────────────────────┐
        │ 难度门（Lean 编译 + Diff 标定） │  [§11.2 的 Diff/Sim 过滤]
        └────────────┬───────────────┘
                     ▼  只放行"刚够得着"的变体
        B: student (RSI-Reap)   ──────┐
        │ reap MCTS + TTT + RL(§05)    │ 验证轨迹：(s,a,verdict,solved)
        ▼                              │
   解出 v_i → 逼近 p_* 的下一变体        │
        │                              │
        ├────────> 累积库 L_{g+1} = L_g ∪ {verified theorems}  ─┐
        │                                                        │
        └────> 新数据集：B 的解轨迹 + 成功/失败对 + 库引用来袭 ─────┤
                     │                                           │
                     ▼                                           │
        A 传统后训练（SFT/DPO 用 B 的数据）  ←────────────────────┘
        （A 变体生成质量提升：教得更好 → B 更快逼近 → 数据更富 → 循环）
```

## 12.2 两个模型各自更新的数据流向

**B（student）拿到**：
- A 生成的课程阶梯 $v_1 \prec \dots \prec p_*$（难度门已过滤 $\mathrm{Diff}\in[0.5,0.9]$）
- B 自己的搜索轨迹（MCTS 已验证/失败样例）→ GRPO/DPO 代际重训（§05）
- TTT：搜索期间单题内的梯度（§09）
- 库上下文 $\mathrm{ctx}(L_g)$（已证引理——B 用它们解更难变体）

**A（teacher）拿到**：
- B 的验证轨迹作为**生成质量偏好数据**：对同一 $p_*$，B 能解决的变体 > 不能解决的变体，形成 DPO 偏好对：

$$\mathcal{D}_A = \left\{(v_{\text{solved}} \succ v_{\text{unsolved}})\ \text{pairs from } L_g \text{ verification}\right\}$$

- 传统 SFT 数据：A 自产变体 + B 的"哪个变体真正帮到 B"反馈 → A 学"什么样的阶梯有效"
- **A 的更新只发生在训练阶段（传统），查询时冻结**——满足"传统方法"约束

## 12.3 交互协议（固定接口，两个模型可独立替换）

```
# A 的一次课程生成请求（B 侧几乎无状态）
POST teacher/variants
{ "target": "theorem p_*（Lean statement text）",
  "library_ctx": ["lemma1: ...", ...],        # 来自 L_g 的检索
  "current_diff": 0.87,                        # B 当前距离（难度门给出）
  "n": 8 }
→ { "variants": [ { "statement": "...", "hierarchy": 1 }, ... ] }

# B → 训练 A 的反馈样本（传统 offline 收集）
{"target": "p_*", "variant": "v_i", "solved_by_student": true, "proof_script": "...", "budget": 64}
```

## 12.4 为什么比单模型 RSI 更好

1. **生成与求解解耦**：生成器不需要懂 MCTS/推理协议，只需要"出题"；可以是商用 API（零训练成本起步），质量迭代靠 B 数据传统后训。
2. **监督信号更干净**：A 的偏好数据是 **B 真解过的**——"教得有效"直接由验证器裁决，比让生成器自评可靠。
3. **库增长惠及双方**：$L_g$ 是 B 的"知识外脑"；对 A 是"出题素材库"（A 出题时可引用库引理，避免生成涉及不存在引理的题目）。
4. **训练预算可拆**：A 用便宜的传统批任务；B 用贵重的 GPU 在线/代际任务——单卡也能错峰。

## 12.5 可控的参数

- A 出题数 / 题、$\mathrm{Sim}\ge \tau$ 阈值、$\mathrm{Diff}$ 区间（初始 [0.5,0.9]）
- B：max_steps、TTT 更新频率（每 k 节点）、$\eta$（错误压降系数 §9.3）
- 环路迭代长度：$g \le G_{\max}$，或求解率持平连续 2 轮即停

## 12.6 与既有文档关系

- §11 的课程/变体/Diff 机制 → 现在由 **A 执行**（本页的 teacher 侧）
- §09 TTT / §10 递归 → 现在由 **B 执行**（本页的 student 侧）

## 12.7 实施顺序

1. **M9** Batch solver（B 的地基，本机可跑）
2. **M13A** A 用现成 LLM API 当 v0 teacher（暂不训练），出变体 → Lean 编译 → Diff 门 → 存 JSONL
3. **M13B** B 学生模式：reap 批量解变体阶梯，记录轨迹；**离线**给 B 做一次 GRPO 代际重训（此时 B 仍是"批式"RSI，等 M8 再加 TTT）
4. **M14** A 的传统后训练：收集 B 的成功/失败对 → DPO → A_v2（教学更准）→ 再来一轮
5. **M15** 累积库 L_g 全面接入：B 解的定理自动登记；A 出题附库上下文；曲线报告

主指标（每代）：teacher 命中率（A 出的变体对 B 的可解率）↑、B 的 $\mathrm{Diff}_{\text{max}}$ 逐代右移、库 $|L_g|$ 与 $\max \mathrm{depth}$ 增长。
