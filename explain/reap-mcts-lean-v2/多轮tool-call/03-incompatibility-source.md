# 03. MCTS × 多轮 tool-call：源码级不相容定位（V2 code v2-code-1）

> 声明：以下全部结论来自 `reap-mcts-lean-v2-code-1/` 实际源码（引用 `文件:行`）。
> 结论：不相容**不是原理性的**，而是**当前 V2 源码尚未实现“多轮”的必要构件**——逐条列出错位、代码证据、以及修复边界。

## 1. 表示层错位（动作与参数的分离）

| # | 证据 | 错位 |
|---|---|---|
| 1 | `mcts_loop.py:59-61`——动作被解析为 `"kind:rest"` 字符串；`eff` 的参数 `in_vals` 由 `self.rng.randint` 随机生成（`:62`） | **参数不在动作里**：树节点只索引"动作类型文本"（`children: dict, key=action_text` `:25,:103`），工具调用的真参数（实验值、检索 query、patch 向量）游离于搜索之外 |
| 2 | `eff_registry.py:35-38`——两个白名单 `sqsum-check/arith-check`，输入纯 Int | 观测类型太细（Int），当前树型动作粒度=“类型”，不是“调用实例” |

**含义**：搜索发生在**动作类型层**，参数层等于“采样时噪音”。工具调用的质量（参数）不受 MCTS 控制——这与“MCTS 应优化工具使用”直接冲突。

## 2. 状态层缺失（观测不入状态 —— 最硬的不相容源）

| # | 证据 | 错位 |
|---|---|---|
| 3 | `mcts_loop.py:104`——`child.state = node.state + " | " + action_text` | **子节点状态是“父字符串拼动作”**——工具调用的**观测输出**（`EffObs.value/ok`，`eff_registry.py:41-51`）**从未并入后续状态**！多轮闭环（run→observe→下一个动作）在状态语义上不存在 |
| 4 | `mcts_loop.py:33-34`——`self.tower` 是单例（共享可变库） | **塔上升 L 不属于节点状态**：A 分支 `adddecl` 会污染 B 分支的 gate/depth 评估 → 树分支失去了状态隔离（`Tower.register` `tower.py:23-27` 是全局 append）。对照设计 $s=(lcx, Env, obs, L)$，L 应在状态内 |
| 5 | `mcts_loop.py:44`——`self.series` 固定实验序列 | "多轮实验" 是**静态玩具**；无“本轮观察→下轮实验设计”的流动 |

**含义**：MCTS 的“状态”与“真实多轮调用的状态”**不同构**。树在“词法历史”上生长，而工具调用依赖“观测图”上生长——这是“不相容感”的最直接原因。

## 3. 结构层（树×时序）

| # | 证据 | 错位 |
|---|---|---|
| 6 | `mcts_loop.py:95`——`while node.children and depth < 4`（路径选择）与 `:101-114`（兄弟并行 evaluate） | **每一步扩展把多候选当兄弟**（并行），但真实多轮是**串行依赖链**（$a_{i+1}$ 依赖 $a_i$ 的 obs）。缺少“效应必须序贯”的结构 |
| 7 | `_evaluate` 对不同 action 的回报是**手写打分**（`:64,:75,:83,:86,:88`、`0.1/-0.2/0.5/-0.3/0.0/-0.5`） | 价值 = 手工规则，**不是由观测驱动的学习值**；真实工具调用价值应来自（a）后验状态质量（b）是否产生入库引理——需要 $V$ 头，而不是 if-else |

**含义**：树搜索遇到了“不可交换动作空间”（工具调用交换律不成立），但实现假定其为“可交换兄弟”。要支持多轮，需要**效应子程序（EffectSubroutine）断言**：把轮串封装为“一个搜索动作”（高维但 tree-able），回到 §5 的“原语化”要求；或者**引入顺序敏感展开**（每轮只取 best action 后再扩子节点）。

## 4. 实现层（成本）

| # | 证据 | 错位 |
|---|---|---|
| 8 | `gate_lean.py:28-30`——每次 gate 都是 `podman run` 全新容器 + 120s 超时 | **gate 冷启动(±2-8s)× 每节点**——CPU 侧多轮工具调用的成本是“节点×容器冷启动”，而非“调用本身”；多轮环境下复用它意味着不可扩展 |
| 9 | `policy_client.py:38-40`——mock 位于本地；`_probe` 端点意外失败即回退 mock（`:48-50`） | 多轮期间策略/值的一致性无保障（mock 可能中途介入） |

## 5. 结论：不相容的三条“真因”与修复清单

**不相容不是二择一，而是缺三个构件**：

| 缺件 | 目标 | 修复建议 |
|---|---|---|
| **T1 观测并入状态** | $T(s,a): (s,\mathrm{obs})\to s'$ | `Node.state` 改为结构化：`(ctx, obs_value, ok_flag, tower_snapshot_idx)`；`EffObs.value` 成为下一轮 prompt 的一部分 |
| **T2 参数结构化动作** | 动作 = 带 schema 的参数实例（非 `"kind:rest"`） | 动作 JSON schema + 约束解码（policy 生成参数，typecheck 校验），树键 = schema 哈希（值不变） |
| **T3 时序包** | 多轮串行链 = 可搜索原语 | `EffectSubroutine(a_1..a_m)` 作为高层动作（§5 原语化），其内部是顺序执行 loop（python 侧），对外是单动作（树层） |

外加两个工程硬改：**T4 塔进入状态**（`Tower` per-node 快照 or 用"提交时 register"模型：分支只在 gate ok 后写库）；**T5 gate 服务化**（起常驻 lean gate server，替代每次 podman run——`gate_lean.py` 改为 HTTP/rpc 接口）。

## 6. 正确的“多轮 × MCTS”架构（基于修复后的源码）

```
多轮 = EffectSubroutine(P)   （顺序执行 a1..am，内部 while budget）
  P 中每一轮：policy → typecheck → run(server) → obs → (并入局部 s̄)
  子程序终止：Ḡ(s̄)（子目标验证 pass/fail）
树层：Subroutine 是单一动作（MCTS 不变）
      ——“多轮”是串行 loop；“搜索”是元层循环：选/选子程序/评估/传播
```
这与我们已有的 `v1_run.py` 的“每个 theorem 一次底层循环”**同构，只是把“tactic 循环”换成“tool 子程序”**。

> 一句话：**当前 V2 代码是“单轮动作 MCTS 原型”**；真正多轮工具调用要加的 T1–T5 恰好就是
> `explain/5-alpha…`（类型化效应语言）与 `多轮tool-call/00/01` 所要求但代码未覆盖的部分——
> 源码定位=把这 5 个缺件标注为 **TODO 主干**：不实现它们，MCTS 与多轮工具调用必然“不相容”。
